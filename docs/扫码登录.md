# 扫码登录 → 只读花名册 → 收推送

这条链路是「原生协议」从 PPT 走向可验证的第一步。三步走，每步都有**可观测的成功判据**：

| 步骤 | 判据 | 说明 |
|------|------|------|
| ① 扫码登录 | 拿到 `keystore.json`，里面有票据 | 证明 ECDH / TEA / code2d / wtlogin 头全对 |
| ② 只读花名册 | 能列出好友与群，数量和手机端一致 | 证明 A2/D2、OIDB 信封、NT 帧全对 |
| ③ 收推送 | 群里发一句话，事件出现在插件里 | 证明服务名订阅与 protobuf 映射对 |

**故意不做发消息**：发送要过 A2 校验 + 频率风控 + 设备信誉，出问题时无法区分
「协议错」还是「被风控」。先把只读跑顺，发送才有排查基线。

## 1. 三步封包

```
0x31 申请二维码
  你 → 服务端   ts | 02 | len | 0031 | 21×00 | 03 | 0000 | 0032 | seq | uin | TLV(16,1B,1D,33,35,66,D1)
  服务端 → 你   sig | TLV(0xD1=QrExtInfo{QrUrl})        ← 给人扫的就是这个 URL

0x12 轮询
  你 → 服务端   appid | sig | uin | TGT | 空 | 空 | TLV 数=0
  服务端 → 你   uin | retry | TLV(0x1E=确认码, 0x19, 0x18)   ← 状态码在 0x1E 首字节

0x13 换票据
  你 → 服务端   uin | code(k) | A2 | guid | 01 | 0001 | 08 | tag 表 | TLV(09,12C,39)
  服务端 → 你   uin | state | ts | platform | TLV(0x106=TGT, 0x10A, 0x10D, ...)
```

状态码（`retCode`，轮询结果的首字节）：

| 值 | 含义 | 是否终态 |
|----|------|----------|
| 48 | 待扫描 | 否 |
| 53 | 已扫码待确认 | 否 |
| 0 | 已确认 | 是（去换票据） |
| 17 | 二维码过期 | 是 |
| 54 | 用户取消 | 是 |
| 144 | 票据无效 | 是 |

实现位置：`arklink/ntqq/code2d.py`（封包）、`session.py`（状态机）。
全部纯函数，`tests/test_ntqq_code2d.py` 用合成响应跑完 0x31→0x12→0x13 全流程。

## 2. 用起来

```bash
# 只打印要发的包，不联网（对拍用）
python -m arklink login --dry-run > 0x31.hexdump

# 真机扫码；票据写到 data/ntqq.json（权限 0600）
python -m arklink login --out data/qrcode.png

# 只读体检：好友数 / 群数，失败了会直接报错而不是假装成功
python -m arklink roster --json
```

挂到 ArkBot 上（`bot.toml`）：

```toml
[[adapters]]
type = "ntqq-native"
qr_login = true                  # 首次扫码；之后靠 keystore_path 复用
keystore_path = "data/ntqq.json"
read_only = true                 # 不发消息
```

第一次启动会在日志里打印二维码 URL（装了 `qrcode` 还会存 PNG）。
拿到票据后 `is_connected` 变真，`get_friend_list` / `get_group_list` 可用；
`send_*` 仍然返回 `1404`，框架自动换通道——这是刻意的。

## 3. 收推送怎么变成 OneBot 事件

服务名 `trpc.msg.olpush.OlPushService.MsgPush`，包体结构见 `push.py` 顶部注释。
映射关系：

| NT Elem | OneBot 段 | 备注 |
|---------|-----------|------|
| `Text` (1) | `text` | 直接取 `TextMsg` |
| `Face` (2) | `face` | `id` = 表情序号 |
| `NotOnlineImage` (4) / `CustomFace` (8) | `image` | `url` 依次尝试 OrigUrl/BigUrl/Url400/Thumb |
| `RichMsg` (12) / `LightApp` (51) | `json` | 卡片原样给 XML/JSON |
| `VideoFile` (19) | `video` | |
| `SourceMsg` (45) | `reply` | `id` = 被引用消息的 seq |
| `CommonElem` type=1 | `at` | uin 为 0 时是 `all` |
| `CommonElem` type=33 | `face` | 小表情 |

`ContentHead.Type == 2` 是撤回，直接出 `notice.group_recall` / `friend_recall`。
遇到不认识的 Elem **不丢事件**：跳过该段，其余照发，`raw` 里留原始字节。

## 4. 还没验证的部分（诚实清单）

这些位置按公开实现对齐了字节布局，但没有真机抓包对拍过，出错时优先看这里：

| 位置 | 风险 | 怎么校准 |
|------|------|----------|
| `code2d` 长度屏障的 `+1` | 差一字节，服务端会回空包 | `login --dry-run` + 真机抓包比长度字段 |
| `encType=4` 重算密钥 | 只有部分场景触发 | 若登录卡在这一步，改用 `encType=0` 分支 |
| `D2Key = MD5(D2)` | 社区通行做法，非官方 | `roster` 返回 401/空时试 `D2` 原值 |
| msfwifi 帧的 4 字节长度前缀 | 不同版本可能多一层握手 | `TcpTransport.recv` 打日志看首包 |
| 好友分页 cookie | 语义未完全确认 | 单页能拉全时 `is_end` 会是 1 |

## 5. 与兼容层的关系

- `ntqq-native` 是**通道**：挂在 ArkBot 下，和 Milky / Satori / 官方 API 并列；
- `arkbot/compat`（在 ArkBot 仓库）是**服务端**：让别的框架接进来；
- 两者可以同时开：ArkBot 用 `ntqq-native` 收，插件用 OneBot 生态写，互不感知。

只读阶段的建议拓扑：

```
QQ 服务器 ──ntqq-native（收推送 / 拉花名册）──┐
NapCat ────milky（发消息，成熟稳定）─────────┤── ArkBot ── 插件
官方 API ──official_qq（兜底）──────────────┘
```

收用新的、发用稳的，是过渡期最省事的组合。
