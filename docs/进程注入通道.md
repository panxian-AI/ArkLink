# 进程注入通道（`ntqq-hook`）

> 目标：**自己登录官方 QQ 客户端 → 程序检测到 QQ 进程 → 注入 → 直接收推送**。
> 不依赖 NapCat / LiteLoaderQQNT，不碰 QQ 的文件，只往一个运行中的进程里放一个 DLL。

## 0. 这条路解决什么问题

| 路线 | 优点 | 死穴 |
|------|------|------|
| `ntqq-native`（原生 SSO） | 完全脱离客户端 | 签名/风控难，发送侧遥遥无期 |
| `ntqq-client`（键鼠） | 零注入、零风险 | 只能发，收不了 |
| **`ntqq-hook`（本通道）** | **收推送实时、完整、可扩展** | 需要客户端在跑；注入有对抗成本 |
| NapCat / LiteLoader | 生态成熟 | 依赖第三方实现存活，被修就死 |

思路来自对 SnowLuma 发行版的逆向（`D:\snow`）：它把一个自包含 DLL 注入
`QQNT` 主进程，DLL 内部加载 `wrapper.node`、起两条命名管道与外部进程通信。
我们把这套结构**自研复刻**，协议自己定，不依赖它的私有实现。

## 1. 架构

```
┌──────────────┐   CreateRemoteThread+LoadLibraryW   ┌────────────────────┐
│  arklink CLI │ ──────────────────────────────────→ │  QQ.exe (QQNT 主进程)│
│  HookQQAdapter│                                     │  ┌──────────────┐  │
│              │ ←──── \\.\pipe\arklink.<pid>.* ──── │  │ arklink-hook │  │
└──────────────┘   control（请求/响应，双向）          │  │   .dll       │  │
        │           recv（推送帧，单向流出）           │  └──────┬───────┘  │
        │                                            │    LoadLibraryW wrapper.node
        ▼                                            │  （后续接内核 API）     │
  push.to_onebot → OneBot 事件                       └────────────────────┘
```

代码分四层，全部可单测（不依赖真 QQ）：

| 模块 | 职责 |
|------|------|
| `arklink/ntqq/hookproto.py` | 40 字节帧协议编解码 + 增量 `FrameReader` |
| `arklink/ntqq/hookproc.py` | 进程发现（区分主进程/渲染进程）、管道探活、注入、安全卸载 |
| `arklink/ntqq/hookpipe.py` | 管道客户端：overlapped I/O、握手、request→ACK→REPLY、重连 |
| `arklink/ntqq/hook.py` | `HookQQAdapter`：检测→注入→连管道→收包转 OneBot 事件 |
| `hookdll/arklink_hook.cpp` | 自研 DLL（管道服务端 + ping/status + uin 探测） |
| `tools/build_hook.py` | mingw-w64 一键编译 x64 DLL |

## 2. 帧协议

借鉴 SnowLuma 的 pipe 帧（`mojo.<pid>.control/recv`，已实测确认），我们用自己的魔数：

```
偏移  大小  字段
0     4    magic  = 0x31504851  ("QHP1" 小端)
4     2    version = 1
6     2    op
8     4    request_id
12    4    status
16    4    flags
20    4    cmd_len      （UTF-8，服务命令名）
24    4    msg_len      （UTF-8，一般为 uin 或错误说明）
28    4    body_len     （原始 protobuf）
32    8    value0       （op=6 时是推送 seq；op=1 时是 pid）
（以上共 40 字节，随后紧跟 cmd + msg + body）
```

op 常量：`1` HELLO / `2` REQUEST / `3` ACK / `4` REPLY / `5` ERROR / `6` PACKET / `7` LOGIN_STATE。
`op=6` 的 `cmd` 是 SSO 服务名（如 `trpc.msg.olpush.OlPushService.MsgPush`）、
`msg` 是 uin、`body` 是原始 protobuf —— 直接喂给 `push.parse_push` 即可转 OneBot 事件。

## 3. 命令行用法

```bash
# 1. 看进程：自动区分 Electron 主进程和渲染/GPU 子进程，并探现有管道
python -m arklink hook --list

# 2. 注入自研 DLL（默认自动挑主进程）
python tools/build_hook.py                                  # 先编译
python -m arklink hook --inject --dll hookdll/build/arklink-hook-x64.dll

# 3. 探事件：连上管道，打印收到的推送（--ping 先验证一次往返）
python -m arklink hook --probe --prefix arklink --seconds 30 --ping

# 4. 卸载（安全顺序：先远程调 ArkLinkPrepareUnload 停线程，再 FreeLibrary）
python -m arklink hook --unload --dll arklink-hook-x64.dll
```

## 4. 挂到 ArkBot

```toml
[[adapters]]
type = "ntqq-hook"          # registry 已注册
auto_inject = true          # 启动时自动检测并注入；false 则只连现成管道
dll_path = "hookdll/build/arklink-hook-x64.dll"
read_only = true            # 目前只放行 get_friend_list / get_group_list / get_status
```

收到的 `op=6` 包经 `push.parse_push` → `push.to_onebot` 变成标准 OneBot 11 事件，
ArkBot 侧零改动。未知段跳过不丢事件，`raw` 保留原始字节。

## 5. 当前状态与边界（诚实清单）

**已经能跑（真机验证过）：**
- 进程发现：9 个 `QQ.exe` 精确挑出主进程，命令行通过 `NtQueryInformationProcess(ProcessCommandLineInformation)` 内联读取（不需要 `ReadProcessMemory`）。
- 注入：`CreateRemoteThread + LoadLibraryW`，远程地址 = 本地模块基址 + PE 导出 RVA（`export_rva()` 自己解析导出表，不需要额外依赖）。
- DLL ↔ 外部：`ping → pong`、`status` 往返正常，overlapped I/O 双通道稳定。
- 卸载：先 `ArkLinkPrepareUnload`（停线程 + `CancelIoEx` + `WaitForMultipleObjects`）再 `FreeLibrary`，实测能干净退出。
- uin 探测：DLL 轮询 `%USERPROFILE%\Documents\Tencent Files\nt_qq_<uin>` 取最近写目录。

**踩过的坑（也是给后来者的雷区）：**
1. **同步管道句柄上读写互锁**：读线程阻塞时同句柄写入永远发不出 → 必须用 overlapped I/O（`FILE_FLAG_OVERLAPPED` + per-read OVERLAPPED 事件）。
2. **卸载顺序**：直接 `FreeLibrary` 会先把代码段撤掉，而工作线程还阻塞在 `ReadFile` → 下次返回跳进已释放内存，QQ 直接消失（我们真把 QQ 带崩过一次）。有 `PrepareUnload` 导出时必须先远程调它并等线程退出。
3. **跨平台 ctypes**：`c_long` 在 Linux 是 8 字节、`c_wchar` 是 4 字节 → 结构体全部用定宽 `c_int32` / `c_uint16 * N`，宽字符手动 UTF-16LE 解码。
4. **`GetProcAddress` 返回值**：直接当函数指针传 `CreateRemoteThread`，不要先 `ctypes.cast(...).value` 再包一层。

**还没做（边界）：**
- DLL 里只实现了管道 + ping/status + uin 探测，**还没调 `wrapper.node` 的内核 API**——收推送目前依赖 DLL 侧后续接入（下一步是仿 SnowLuma 的 `loadModuleManual` 加载 wrapper 并转发其 SSO 包到 `recv` 管道）。
- 注入方式只有 `LoadLibraryW`（容易被 QQNT 的模块白名单/完整性检查发现），manual map 在待办里。
- 风控对抗没有做：注入本身有封号风险，建议小号先行。

## 6. 与 SnowLuma 的关系

`D:\snow` 是私人发行版，我们只逆向了它的**协议形态**（帧格式、op 语义、管道命名），
没有复制它的代码，也没有链接它的 DLL。`hookdll/` 是从零写的自研实现，
帧协议换成自己的魔数，后续想接它的 DLL 也只需要改一个前缀（`--prefix mojo` 就能连它的 `mojo.<pid>.control`，前提是它没在跑——它的 control 管道是单实例独占的）。
