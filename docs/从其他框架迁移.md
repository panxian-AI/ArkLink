# 从其他框架迁移过来

这份文档只回答一个问题：**我现在跑着一套 bot，怎么换成 ArkLink，要动多少东西。**

先说结论：绝大多数情况只改**地址**，不改代码。因为 ArkLink 对外就是一个
OneBot 11 实现（和 NapCat 同形状），对内可以挂任意协议端。

---

## 0. 先搞清楚你有几个仓库要换

这套东西分两个仓库，职责不同，**升级和回退也要分开做**：

| 仓库 | 是什么 | 里面的东西 | 什么时候需要动 |
|------|--------|-----------|---------------|
| [ArkBot](https://github.com/panxian-AI/ArkBot) | 框架内核 | 插件系统、规则、消息链、调度、发件箱、官方 Bot 通道、OneBot 11 兼容层 | 你写业务逻辑，或者想让 NoneBot2/Koishi 连上来 |
| [ArkLink](https://github.com/panxian-AI/ArkLink) | 协议外挂层 | Milky / Satori / ntqq-hook / ntqq-native / ntqq-client / OneBot 服务端 | 你要「怎么连上 QQ」 |

对照自己的情况选一条：

- **只用过 NapCat，上层是 NoneBot2 / Koishi** → 只需要 ArkLink（情况一），完全不用装 ArkBot；
- **已经在用 ArkBot** → 只装 ArkLink，`bot.toml` 加一个 adapter（情况三）；
- **什么都没有，从零开始** → 先 ArkBot（业务）+ ArkLink（通道），两个都装。

两者版本号是**独立的**（ArkBot 现在 0.4.0，ArkLink 0.6.0），不要混着看。

---

## 情况一：现在用 NapCat / Lagrange / LLOneBot（最常见）

这三个都是 OneBot 11 协议端，你的上层（NoneBot2 / Koishi / AstrBot / 自研脚本）
连的是它们的 HTTP/WS 地址。迁移就是**把协议端换掉**：

```bash
# 1. 关掉旧协议端（别两个一起连，会互相抢消息）
# 2. 打开官方 QQ 客户端并登录（我们借用它的会话，不需要密码）
# 3. 注入 + 起服务端
python -m arklink hook --install
python -m arklink serve onebot --port 6700 --token 你的token
```

然后改上层配置里的地址：

| 上层 | 原来 | 现在 |
|---|---|---|
| NoneBot2 正向 WS | `ws://127.0.0.1:3001` | `ws://127.0.0.1:6700/onebot/v11/ws` |
| NoneBot2 反向 WS | 填 NapCat 的地址 | 填 `ws://127.0.0.1:6700/onebot/v11/ws` |
| Koishi | OneBot 适配器 + `3001` | 同上，端口换 6700 |
| AstrBot | `ws://127.0.0.1:6199/ws` | `ws://127.0.0.1:6700/onebot/v11/ws` |
| 自研 HTTP | `http://127.0.0.1:3000/send_group_msg` | `http://127.0.0.1:6700/send_group_msg` |

**代码一行都不用改。** 事件格式、段数组、`retcode` 语义都是 OneBot 11 标准。

> 差异只有一个：ArkLink 目前**发送**能力还依赖 hook 模块（见文末状态表）。
> 未实现的接口返回 `retcode=1404` 而不是 500，你的框架会按标准降级。

## 情况二：现在用 SnowLuma（或别的 hook 客户端）

SnowLuma 被封/不可用时，它对外仍然是 OneBot 形状，所以迁移路径和情况一相同。
不想装两套就：

```bash
python -m arklink hook --list        # 看还有没有残留管道（mojo.<pid>.control）
python -m arklink hook --install     # 用 ArkLink 自己的模块接管
python -m arklink serve onebot --port 6700 --token t
```

注意：SnowLuma 的 control 管道是**单实例独占**的。如果它还在跑，先退掉它，
否则两边打架（`--list` 会显示 `busy`）。

## 情况三：现在用 ArkBot 的 `onebot11` 适配器

ArkBot 本身不用换，只换「怎么连 QQ」：

```toml
# 之前：连 NapCat
[[adapters]]
type = "onebot11"
url = "ws://127.0.0.1:3001"

# 现在：直接加载注入通道（少一层）
[[adapters]]
type = "ntqq-hook"
auto_inject = true
read_only = true
```

或者在 ArkBot 里继续用 OneBot 适配器，把它指向 ArkLink 的 `serve onebot` 端口 ——
适合「先验证，再切直连」的渐进迁移。

插件、规则、消息链、调度**全部不动**：它们写在 ArkBot 内核层，和通道无关。

---

## 情况四：现在用别的框架（不是 OneBot）

比如自己写的脚本直接调 NapCat 的 HTTP。分两步：

1. **第一步**：把 HTTP base_url 换到 `http://127.0.0.1:6700`，token 换掉，先跑通。
   这一步之后你已经在用 ArkLink 了，只是调用方式没变。
2. **第二步（可选）**：换成 ArkLink 的 Python 契约（`LinkAdapter`），
   省掉一层 HTTP，直接 `await adapter.call_api(...)`。

## 迁移对照表：API 差异

| OneBot 11 接口 | ArkLink 现状 |
|---|---|
| `send_group_msg` / `send_private_msg` / `send_msg` | 🟡 hook 通道目前只读（1404）；`milky`/`satori` 通道正常 |
| `get_login_info` / `get_status` | ✅ |
| `get_group_list` / `get_friend_list` | 🟡 hook 返回 1404（走 `ntqq-native` 可拉花名册） |
| `delete_msg` / `set_group_ban` 等管理类 | 🟡 取决于底层通道能力，未实现即 1404 |
| 事件：`message` / `notice` / `meta_event` | ✅ 段数组与 NapCat 一致 |
| 鉴权：`Authorization: Bearer` / `?access_token=` | ✅ |
| 正向 WS + HTTP API + HTTP 上报（同端口） | ✅ |
| WS 路径 `/`、`/onebot/v11/ws`、`/api/ws`、`/ws` | ✅ 四个都认 |

## 迁移前检查清单

```bash
# 1. 当前版本、有没有新版
python -m arklink version

# 2. 通道能起来吗（QQ 已登录的前提下）
python -m arklink hook --list

# 3. 服务端能起来吗（不依赖 QQ，先验证端口/鉴权）
python -m arklink serve onebot --port 6700 --token t
curl -H "Authorization: Bearer t" http://127.0.0.1:6700/

# 4. 上层连上后，看服务端日志有没有 lifecycle/connect
```

建议顺序：**先并行跑**（旧协议端 + ArkLink 各占一个端口，上层切一份配置试），
确认事件能收到、能发出去，再停旧的。别直接删旧配置 —— 回退成本会变高。

## 出问题了怎么回退

两个仓库分别回退（`--project` 决定动哪个）：

```bash
python -m arklink versions --project arklink     # ArkLink 的历史版本
python -m arklink update --to 0.5.0              # 先看会执行什么命令（不真装）
python -m arklink update --to 0.5.0 --yes        # 真装

python -m arklink versions --project arkbot      # ArkBot 的历史版本
python -m arklink update --project arkbot --to 0.3.0 --config bot.toml
python -m arklink update --project arkbot --to 0.3.0 --yes
```

`--config` 指向你的 `bot.toml`，回退检查会据此推断你在用哪些能力。

回退前会自动检查：目标版本有没有你现在用的功能。例如你现在用 `ntqq-hook`（0.3.0 起）
和 Linux 注入（0.5.0 起），回退到 0.2.0 会直接拦住（ArkBot 同理，比如把
`[compat]` 兼容层往回退到 0.4.0 之前）：

```
回退到 0.2.0 会导致以下功能不可用：
  - Windows 注入通道（ntqq-hook）（需要 0.3.0+）
  - Linux 注入通道（ptrace + Unix socket）（需要 0.5.0+）

确认要继续请加 --force。
```

确认要降级就加 `--force`，但请注意旧版本可能读不懂新版本的配置文件。

**不想被提醒新版本**：

```bash
python -m arklink update --disable-check     # 永久关闭（写 ~/.arklink/state.json）
python -m arklink update --enable-check      # 恢复
export ARKLINK_NO_UPDATE=1                   # 临时关闭（CI 里建议设上）
```

## 附：现在的真实状态

| 能力 | 状态 |
|---|---|
| OneBot 11 服务端（WS/HTTP/上报/鉴权/心跳） | ✅ 181 项测试 |
| 注入链路（进程发现 / 注入 / 管道 / 卸载） | ✅ Windows 真机验证；Linux CI 验证 |
| 收到 QQ 推送 | ❌ 待接客户端消息分发（DLL/.so 侧） |
| 发送消息 | ❌ 只读，返回 1404 |

**所以现在适合「先接入、先验证链路」，不适合直接替换掉生产里的 NapCat。**
等收/发接上，这份迁移文档的结论会变成「直接换」。
进度见 [协议级封禁.md](协议级封禁.md)。
