# 发消息链路

> 状态：**0.8.0 已打通**（UI 通道真机验证：1000000001 → 示例好友，消息落到会话里）。
> 本文讲清「现在怎么发、为什么这样发、1.0 还差什么」。

## 一、现在能做什么

```
arklink send --to 示例好友 --text "hi"          # 默认 dry-run，只演练
arklink send --to 示例好友 --text "hi" --yes    # 真的发
```

也可以从 OneBot 11 服务端发（上层框架零改动，`send_msg` / `send_private_msg` /
`send_group_msg` 都接到了同一条链路）。

硬约束（写在代码里，不是配置自觉）：

* 只允许账号 **1000000001** 发；别的号一律 `1403`。
* 只允许发给白名单里的人（默认 **示例好友**）；没扫过花名册也认「白名单点名的名字」，
  但白名单之外一律拒绝。
* 群聊默认关闭；图片/语音等非文本段拒绝并报 `1400`，让上层换通道，不静默丢。

## 二、三条路线，为什么先走第二条

| 路线 | 原理 | 状态 |
|------|------|------|
| A. 协议层（`MessageSvc.PbSendMsg`） | 自己拼 protobuf，借客户端的 SSO 会话发 | 参照实现是 SnowLuma；需要 DLL 转发原始包，未做 |
| B. 操作官方客户端（UI 通道） | 按账号认窗口 → 搜索会话 → 粘贴 → 回车 | **已打通，0.8.0 默认引擎** |
| C. 进程内直调（`KernelMsgService::sendMsg`） | 远程调用客户端自己的发送函数 | ABI 已逆向（见下），卡在实例发现，未做 |

选 B 不是妥协，而是当前证据下的最优解：

* **消息由官方客户端产生**。不拼包、不伪造协议，风控看到的就是「用户在打字」，
  这是整个项目「零协议改写」战略在发送侧的落实。
* A 和 C 都必须先把 DLL 变成真正的业务 hook（现在的 DLL 只是管道骨架），
  那是收消息同一道坎，不该被发送堵在半路。

## 三、UI 通道的关键细节（都是真机踩出来的）

1. **认号**：一台机器登两个号时，两个 `QQ.exe` 的窗口标题都叫 "QQ"。
   解法是内存指纹——自己的号在自己的进程里出现的次数比「别人的号」高两个数量级
   （实测 632 vs 6），`qqabi.whoami()` 按 3 倍优势判定，认不出来就拒绝盲发。
2. **入口**：`Ctrl+F` 打开的是「综合搜索/加好友」，不是会话搜索——第一次实测就进了
   加好友页。正确入口是**会话列表顶部的搜索框**（窗口内相对坐标 150,65）。
3. **选中联系人**：用鼠标点第一条结果（210,156），不要回车——回车在综合搜索里
   会跳加好友。
4. **焦点**：`SetForegroundWindow` 经常被系统拒绝；不确认前台就把粘贴和回车敲出去，
   文本会落进用户正在用的编辑器。所以每次聚焦都验证前台，拿不到就放弃。
5. **输入框**：聊天区底部约 65% 宽、87% 高处（9.9.31 默认布局实测），
   可用 `input_xy` 参数校准。

## 四、进程内直调（路线 C）逆向到了哪一步

`wrapper.node`（9.9.31-49738）：

* 导出表修饰名给出签名：
  `void KernelMsgService::sendMsg(int64 msgId, const Contact&, const vector<MsgElement>&, const unordered_map<int,MsgAttributeInfo>&, const shared_ptr<IOperateCallback>&)`
* napi 属性描述符 `{name:"sendMsg", method:0xE40BCC}` → JS 包装；
* RTTI 反查主 vtable：`0x39A5888`，槽位 30（`+0xF0`）→ `0x2C5E86`，两者都在运行进程里
  核对过（读 vtable 第 30 槽等于预期地址）；
* `Contact`：`{int32 chatType; string peerUid(+0x08); string guildId(+0x20)}`，共 0x38 字节。

**卡点**：全进程扫描（两个主进程各扫 ~830MB）发现——没有任何对象的 vtable 指针
指向 `0x39A5888`，`sendMsg` 的实现地址在堆里也只出现在那张静态表里。
结论：这个版本的消息服务不是以「对象首地址 = 该 vtable」的形式存在（派生实现 +
内部总线转发）。要拿 `this`，必须 hook 一次真实发送抓模板——这和收消息的 hook
是同一件事，所以路线 C 与收消息一起在 1.0 做，不单独硬啃。

复现工具：`arklink/ntqq/qqabi.py`（`probe()` 只读探针，`--probe` 打印结论）。

## 五、并发与突发（真实环境必踩）

真实场景不是「一次一条」：告警会连着来、一个通知要发给多个人。UI 通道只有一个窗口，
并发操作会互相抢焦点、把文字粘进错误的输入框，所以引擎层做了三件事：

| 机制 | 做什么 | 为什么 |
|------|--------|--------|
| 全局串行锁 | 同一个时刻只允许一个窗口操作 | 抢焦点必然错乱，宁可排队 |
| 最小间隔 `min_gap`（0.35s） | 相邻两条之间强制间隔 | 客户端对连发有节流，抢太快会丢 |
| 顺序队列 + 深度上报 | `pending` / `queue_depth` 公开给 WebUI | 突发时看得见"还在排队"，不是卡死 |

`SendService.send_many(targets, message)` 支持一次发给多个对象：
结果列表与入参**一一对应、顺序一致**，中间某个对象被策略拒绝（比如不在白名单）
只影响它自己，不会中断后面的。

多条消息按行拆：WebUI 里一行一条，按「先内容后对象」的顺序发，
即 `第1条→A、第1条→B、第2条→A、第2条→B`，保证同一个人收到的顺序与输入一致。

## 六、WebUI

```bash
python -m arklink serve webui --port 6800                       # 默认只监听 127.0.0.1
python -m arklink serve webui --port 6800 --password 你的口令    # 口令登录（推荐）
python -m arklink serve webui --port 6800 --token t             # 也可以只用 token
```

设计上借鉴了 SnowLuma 的 WebUI 几处做法（它的前端是独立 bundle，我们没有照搬代码）：

* **口令登录 + cookie 会话**，而不是把 token 拼在地址栏里——地址会进历史记录、
  也会被截图带出去；
* **日志面板**：`logging` 挂一个环形缓冲（500 行），页面底部直接看，
  排障不用回终端翻；
* **配置面板**：账号白名单、收件人、群聊开关、单条上限、排队深度一屏看全
  （只读，改配置仍走配置文件，避免"网页改一半"的状态）；
* **单端口同源**：页面、API、日志都在这一个进程里，没有跨域和额外服务。

一页看全：发送引擎状态、官方客户端（在线/账号/窗口）、QQ 进程与管道、策略闸门、
发送记录、体检结果。发送区支持：

* 多个收件人：`示例好友,示例好友2`（逗号分隔，每个都要过白名单）
* 多条消息：一行一条，按顺序发
* 默认勾选「演练」——先看策略判定再真发，和 CLI 的 `--yes` 同一套规矩

接口（都能直接用 curl / 脚本调）：

```
GET  /api/status      GET  /api/history?limit=20
GET  /api/doctor      GET  /api/peers
POST /api/send        {"to":"示例好友","text":"hi","dry_run":true}
```

安全边界：默认只听 `127.0.0.1`；它能用你的账号发消息，暴露到公网等于交出账号。
非本机监听且没设 token 时，启动时会打印醒目警告。

## 七、能不能不抢焦点（最小化后台发送）

**当前不能。** UI 通道的本质是「模拟用户在窗口里操作」，而 Windows 只把键鼠输入
送给前台窗口，所以每次发送都会把 QQ 弹到最前面、占用剪贴板。这对「不影响其他程序」
是硬冲突——不是实现粗糙，而是这条路的上限。

三条可能的替代路线，都试过或评估过：

| 路线 | 结论 |
|------|------|
| 后台 PostMessage 发按键 | Chromium 不处理合成消息，输入框收不到字符 |
| UIA 无障碍（InvokePattern / ValuePattern，无需焦点） | 实测 QQ 的 UIA 树只有空 Pane——Chromium 无障碍没开（可用 `--force-renderer-accessibility` 启动，但要改启动方式） |
| 进程内直调 `KernelMsgService::sendMsg` | 唯一真正无窗口、无焦点、无剪贴板的方案；卡在实例发现（见第四节） |

所以「后台发送」不是一个开关，而是 1.0 的核心工作：把 hook 那一脚补上。
在补上之前，UI 通道只在**无人值守但有前台**的场景可用，并且每次发送都会抢一次焦点——
这一点必须在文档和 WebUI 里说清楚，不能假装它是后台的。

## 八、1.0 清单（对齐 NapCat / SnowLuma 的「等价替代」）

0.8.0 已经有：发送（UI 通道）+ 策略闸门 + OneBot 11 服务端 + 注入骨架 + 体检/迁移/版本管理。

1.0 的验收线是「收发闭环」：

1. **收消息 + 后台发送**：DLL hook 到客户端消息分发点（收）与 `KernelMsgService`
   （发）。一次 hook，两件事：`this` 拿得到，发送就不用窗口、不抢焦点、不用剪贴板。
   `hook.py` 的接收侧和 `send.py` 的 `PipeEngine` 都已留好插口。
2. **发送升级**：同一个 hook 抓到 `KernelMsgService` 实例后，`PipeEngine`
   接管发送（`send.py` 的引擎接口已留好，换实现、上层零改动）。
3. **媒体消息**：图片发送（需要客户端的上传入口，路线 C 通了才有）。
4. **UI 通道退役为兜底**：保留给「协议端全被封」的场景。

风险提示：所有进程内动作都可能让 QQ 崩溃（卸载顺序、线程时序都有讲究），
真机验证一律先只读探针，再动内存。
