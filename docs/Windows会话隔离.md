# 在 Windows 上「另开一个桌面」：四种做法，只有一种可行

> 结论：**虚拟桌面（Win+Ctrl+D）和 CreateDesktop 都不行**，它们共享同一条输入队列；
> 唯一可行的是 **独立登录会话（快速用户切换）**——每个会话有自己的 WinSta0、自己的
> 输入队列、自己的剪贴板。把 QQ 放进会话 2，主会话就完全不受影响。

## 一、问题出在哪：Windows 只有一个输入队列

| 资源 | 作用域 | 后果 |
|------|--------|------|
| 输入队列（键盘鼠标 / `SendInput`） | **每个会话一份** | 同一会话内所有进程共用，打到「前台窗口」 |
| 剪贴板 | **每个会话一份** | 同会话内全局共享，发送时会占用 |
| `WinSta0\Default` 桌面 | **每个会话一份** | 所有可见窗口都在它上面 |
| 前台窗口（`SetForegroundWindow`） | 每个会话一个 | 想输入就必须先把它顶到前台 |

所以「不影响其他程序」的本质条件是：**QQ 和你的工作窗口不在同一个输入队列里**。
判断方法只有一条——`SessionId` 是否相同。

```powershell
Get-CimInstance Win32_Process -Filter "Name='QQ.exe'" |
  Select-Object ProcessId, SessionId
```

本机实测：两个 QQ 主进程 `35472` / `31368` 都在 **Session 1**，和你现在用的浏览器、
编辑器同一个会话。这就是为什么每次发送都得把 QQ 顶起来。

## 二、四种「另开桌面」的真实能力

### 1. 虚拟桌面（Win+Ctrl+D、任务视图）——❌ 没有隔离

它只是 DWM 的**显示过滤**：哪几扇窗画给用户看。底层仍是同一个
`WinSta0\Default` 桌面、同一条输入队列、同一份剪贴板。

更糟的是反作用：调用 `SetForegroundWindow` 去激活另一个虚拟桌面上的窗口时，
**Windows 会把用户的视图直接切到那个桌面**。比"弹到上层"更难接受。

结论：虚拟桌面解决的是「窗口太多看着乱」，不是「输入冲突」。方向不对。

### 2. `CreateDesktop()` 新建桌面（同一窗口站）——❌ 要翻屏

`CreateDesktop` + `STARTUPINFO.lpDesktop` 确实能把 QQ 放进一个看不见的桌面。
但 `SendInput` 只投给**当前输入桌面**（input desktop）。想让按键进到新桌面，
必须 `SwitchDesktop()` —— 物理屏幕会**立刻切**到那个桌面，用户眼前一花。
用完再切回来会有明显黑屏闪断，而且这中间任何并发输入都会打错窗口。

结论：这条路只是把「抢焦点」换成了「抢整个屏幕」。

### 3. 独立窗口站（`CreateWindowStation`）——❌ 没有输入队列

不同窗口站之间确实是隔离的（服务就是这么跑的）。代价是：**非交互式窗口站没有
输入队列**，`SendInput` / `keybd_event` 直接失败（`ERROR_ACCESS_DENIED`），
只剩 `PostMessage`。

而 Chromium 不响应合成的 `WM_CHAR` / `WM_LBUTTONDOWN`（已实测：消息返回成功，
界面毫无反应），UIA 树在没开无障碍时也是空的。所以这条路在 QQ 上走不通。

### 4. 独立登录会话（快速用户切换）——✅ 唯一可行

每个登录会话都有自己的 `WinSta0`、自己的输入队列、自己的剪贴板。把 QQ 放进
**会话 2**，`SendInput` 就只进会话 2 的队列，会话 1 里你正在打字的窗口一个字符都
不会错。

前置条件（本机已满足）：

* Windows 客户端 SKU 支持多会话并存（家庭版/专业版都支持快速用户切换）；
* `HideFastUserSwitching` 未设为 1（默认就是允许）；
* 机器上有第二个本地账户（本机已有 `pan`）。

## 三、怎么搭（一次，约 10 分钟）

```powershell
# 0) 确认当前状态：谁在哪个会话
python tools/check_session.py

# 1) 需要一个第二账户（已存在就跳过）
#    net user qqbot <密码> /add

# 2) 切到第二账户登录一次（Win+L → 切换用户），在那边装/启动 QQ 并扫码
#    注意：QQ 数据目录按用户隔离，所以这里必然要重新登录一次

# 3) 在会话 2 里装好 Arklink，并让它跟着登录自启（计划任务，触发器=用户登录）
schtasks /create /tn ArkLink /tr "pythonw -m arklink serve webui --port 6800 --engine host --host 0.0.0.0" `
         /sc onlogon /ru pan /rl highest
#    也可以放进 shell:startup

# 4) 切回你的主账户。会话 2 变成「断开」状态，QQ 与 Arklink 继续运行

# 5) 主账户浏览器打开 http://localhost:6800 —— 跨会话的 loopback 是通的
```

关键验证（切回主账户后跑）：

```powershell
python tools/check_session.py
```

它必须报告：**QQ 进程的 SessionId ≠ 当前进程的 SessionId**，且给出「隔离已生效」
的结论。若两者相同，说明你还在原来的会话里，注入会抢你当前窗口的焦点。

## 四、和其他方案的成本对比

| 方案 | 额外内存 | 磁盘 | 需重新登录 QQ | 后台发送 | 备注 |
|------|---------|------|--------------|---------|------|
| **Windows 独立会话** | 0（QQ 本来就要跑） | 0 | 一次（换用户 = 换数据目录） | ✅ | 需要一个第二账户；重启后要重新登录会话 2 |
| Linux 容器 + Xvfb | ~1.2GB | ~1GB | 一次（扫码） | ✅ | `docs/无头Linux运行.md`，跨平台、可迁到服务器 |
| Windows 虚拟机 | 4GB+ | 20GB+ | 一次 | ✅ | `VBoxManage controlvm keyboardputstring` 可无头注入，最贵 |
| 同会话 UI 通道（现状） | 0 | 0 | 不需要 | ❌ | 会抢焦点、占剪贴板 |

**如果只是为了「后台」，独立会话比 Linux 容器更划算**——省 1.2GB 内存和一整套环境。
Linux 方案的优势在别处：能放进服务器、能一机多号彻底隔离、不受 Windows 更新影响。

## 五、限制（必须提前知道）

1. **会话 2 必须被登录过一次**。Windows 没有「未登录会话跑 GUI 程序」这回事，
   session 0 是服务隔离区，跑不了 QQ。
2. **重启后会话 2 不会自动恢复运行**。要么每次手动切过去登录一次，要么配
   `AutoAdminLogon`（明文密码进注册表，安全上有代价），要么用计划任务 +
   自动登录组合。
3. **切回主账户后，会话 2 的屏幕看不到**。要肉眼看 QQ 界面就再切回去，
   或者从另一台机器 RDP —— 注意客户端 SKU 的 RDP 会**接管**会话，不会新开。
4. **一个会话一个号最稳**。同一会话里跑两个号，输入队列又合并了，认号问题回来。
   两个号要隔离，就两个会话（或一个会话 + 一台 Linux）。
5. **注入仍依赖窗口坐标**。会话隔离解决的是「不影响别人」，不解决「不依赖界面」。
   要做到完全不碰窗口，得靠 CDP / UIA（见下节）。
6. **音频/摄像头**：会话 2 断开时没有音频设备，QQ 语音会异常，纯文字收发无影响。

## 六、还有一条更干净的路：给 QQ 开调试通道

会话隔离是「关在另一个房间里手动操作」，CDP 是「直接跟它的页面说话」——
不碰鼠标键盘，连窗口都不需要存在。

QQ NT 是 Chromium 内核，理论上认这两个启动参数：

| 参数 | 能得到什么 | 代价 |
|------|-----------|------|
| `--remote-debugging-port=9222` | CDP：`Runtime.evaluate` 找输入框、`Input.insertText` 填字、`Input.dispatchKeyEvent` 回车。**全程不碰焦点、不碰剪贴板** | 需带参数重启 QQ 一次；端口要只绑 127.0.0.1 |
| `--force-renderer-accessibility` | 打开无障碍树，UIA 就能读到真正的控件（现在我们探到的只有空 Pane），可用 ValuePattern 后台赋值 | 需带参数重启 QQ 一次 |

两条都要**重启 QQ**（当前进程命令行是干净的 `"...\QQ.exe"`，没有附加参数），
所以属于「有代价的验证」，得先确认可以接受一次重登。
验证成本很低：带参数启动后看 `Get-NetTCPConnection -LocalPort 9222` 是否有监听。

只要其中一条通，Windows 侧就不需要虚拟桌面、不需要 Linux、不需要会话隔离，
`PipeEngine` 那层抽象可以直接换成 `CdpEngine` 或 `UiaEngine`。

## 七、和现有代码的关系

`host` 引擎**不需要改动**：它本来就是在「当前会话」里用 `SendInput` 操作窗口。
放到会话 2 里跑，行为不变，但影响范围自动收窄到会话 2。

需要改的只有部署方式：

* WebUI 监听 `0.0.0.0` 或 `127.0.0.1`，主会话用 `http://localhost:6800` 访问；
* 白名单策略（`sendpolicy.py`）与会话无关，照旧；
* `tools/check_session.py` 用于自检「我到底在哪个会话、QQ 在哪个会话」。
