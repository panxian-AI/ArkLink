# QQ 协议地图与逆向分析

本文回答三个问题：

1. 现在能用的 QQ 接入协议有哪几条路，各自死在哪一层？
2. 官方开放协议（合规路线）到底能给到什么能力，限制在哪？
3. QQ NT 原生协议逆向到哪一步了，还差什么，怎么继续？

> 结论先行：**没有任何单一协议能长期稳定**。所以 ArkBot 的架构是
> 「多通道并行 + 来源通道路由 + 离线发件箱 + 全通道不可用时官方兜底」。
> 本仓库负责把「协议」这一层做成可插拔的外挂。

---

## 1. 三层结构：ban 到底发生在哪一层

```
┌──────────────────────────────────────────────────────────────┐
│ 应用层协议   OneBot 11 │ Milky │ Satori │ 官方 Bot API        │  ← 只描述"消息长什么样"
├──────────────────────────────────────────────────────────────┤
│ 中间层实现   NapCat / Lagrange / LLOneBot / Chronocat …       │  ← hook 客户端 / 模拟登录
├──────────────────────────────────────────────────────────────┤
│ 传输层       NTQQ 内部 SSO 封包（TEA + protobuf + qsign）      │  ← 真正的“地壳”
└──────────────────────────────────────────────────────────────┘
```

关键事实：**上层协议本身不违规**，它们只是 JSON 约定；风险来自中间层——
中间层要么 hook 官方客户端，要么模拟登录，这两件事才是 QQ 风控与版本更新打击的对象。

由此得出两个推论：

- 换上层协议（OneBot → Milky → Satori）**不降低风险**，只是换了个壳。它的价值是
  「某个实现被针对时，业务代码不用改」；
- 真正能绕过「逆向全灭」的只有**官方 API**，代价是能力受限。两者必须同时具备。

---

## 2. 各通道对照表

| 通道 | 协议性质 | 封禁风险 | 能力上限 | 身份 | 本仓库/主仓状态 |
|------|----------|----------|----------|------|------------------|
| OneBot 11 | 事实标准（逆向侧） | 高：实现被针对即失效 | 全（群/私聊/富媒体/管理） | 真实 QQ 号 | ArkBot 主仓 `adapters/onebot11.py` |
| **Milky 1.3** | 新标准（逆向侧，强类型） | 与 OneBot 同源，同生共死 | 全 | 真实 QQ 号 | **本仓库 `arklink/milky.py`（可用）** |
| **Satori v1** | 跨平台（Koishi 生态） | 取决于底层 SDK | 全（取决于 SDK） | 真实 QQ 号 | **本仓库 `arklink/satori.py`（可用）** |
| 官方 Bot（群/C2C v2） | 官方 | **无**（合规） | 受审核与配额限制 | openid（非 QQ 号） | ArkBot 主仓 `adapters/official_qq.py` |
| 官方频道 Guild | 官方 | 无 | 频道场景 | guild/user id | 同上（同一套网关） |
| **QQ NT 原生 SSO** | 逆向（协议层） | 最高：直接模拟客户端 | 理论全 | 真实 QQ 号 | **本仓库 `arklink/ntqq/`（研究态）** |
| **操作官方客户端** | 外部键鼠（不注入） | 低：不碰客户端内部 | 只发文本、只发不收 | 真实 QQ 号 | **本仓库 `arklink/ntqq/host.py`** |

「同生共死」是重点：Milky / Satori 的协议端仍然跑在 NapCat / Lagrange 这类
实现之上。**如果 QQ 从客户端侧掐掉了 hook 点，它们一起失效。**
所以 Milky/Satori 解决的是「生态迁移成本」，不是「抗封」。

## 3. 官方开放协议（合规路线）

这是唯一不会因为「逆向被修」而消失的通道，值得认真对待。

### 3.1 两套 appid，两套能力

| 类型 | 入口 | 能收到什么 | 能发什么 |
|------|------|------------|----------|
| 群机器人 | q.qq.com 创建，沙箱 → 提审上架 | 群内 @机器人、单聊 | 群消息（被动优先）、C2C |
| 频道机器人 | QQ 开放平台 → 频道 | 频道 @、频道私信 | 频道消息 |

同一条 HTTPS 网关（`api.sgroup.qq.com`），同一套鉴权与事件格式，所以
ArkBot 一个适配器就能同时覆盖两者。

### 3.2 鉴权与网关时序

```
POST https://bots.qq.com/app/getAppAccessToken
     {"appId": "...", "clientSecret": "..."}
  →  {"access_token": "...", "expires_in": 7200}          # 必须缓存，重复取会被限流

GET  https://api.sgroup.qq.com/websocket                  # 拿 wss 地址（带鉴权头）
WS   OP 10 HELLO  {heartbeat_interval}
  →  OP 2 IDENTIFY {token: "QQBot <access_token>", intents, shard}
  →  OP 0 READY    {session_id, user}
     OP 1 心跳（带上次 seq） → OP 11 ACK
     断线重连：OP 6 RESUME（带 session_id + seq），无 resume 用 OP 2
```

### 3.3 事件与回复

| 事件 | 说明 | 关键字段 |
|------|------|----------|
| `GROUP_AT_MESSAGE_CREATE` | 群里被 @ | `id`(msg_id) / `group_openid` / `author.member_openid` |
| `C2C_MESSAGE_CREATE` | 单聊 | `id` / `author.user_openid` |
| `AT_MESSAGE_CREATE` | 频道被 @ | `channel_id` / `guild_id` |

发消息：

```
POST /v2/groups/{group_openid}/messages
     {"content": "文本", "msg_type": 0, "msg_id": "<被动回复必填>"}
```

- **带 `msg_id` = 被动回复**：免费、限时（分钟级）、有次数上限；
- **不带 `msg_id` = 主动消息**：受每日配额约束，超了直接失败。

### 3.4 硬限制（决定了它只能当兜底）

- 拿到的是 **openid**，不是 QQ 号：跨群不可关联、无法查资料、无法主动加好友；
- 不能读历史消息、不能进未授权的群、不能主动拉群；
- 富媒体需要先上传素材，卡片/按钮走 Ark 模板，自由度远低于 CQ 码；
- 必须提审上架，个人开发者有类目与资质限制。

ArkBot 的做法是：`official_qq` 适配器把 openid 用 CRC32 映射成稳定的伪 QQ 号，
插件层照旧用数字 ID 工作，于是「官方通道 vs 逆向通道」对插件完全同构。
**这是双通道无感切换能成立的前提。**

> 配额、事件名、接口路径以官方最新文档为准；上面的数字仅用于说明「有限」。

## 4. 为什么「影分身」容易被踢，而操作真实客户端不会

这是实践里最先撞到的一堵墙：**自己跑登录（headless / 协议端）的号，隔几小时到几天就被踢；
而桌面上挂着的官方 QQ，一直好好的。** 不是协议写错了，是「谁在替你心跳」不一样。

### 4.1 官方客户端实际维持了什么

| 客户端在做的事 | 自实现登录通常缺 |
|----------------|------------------|
| 设备指纹（guid / qua / 机型 / 安装 ID）稳定不变 | 每次重建或伪造不一致 → 判为异常设备 |
| 登录态心跳与 ticket 续期 | 只拿到初始 ticket，过期即失效 |
| 在线状态上报、已读回执、埋点 | 完全没有 → 「在线但没有任何行为」很可疑 |
| 版本号、灰度、风控 SDK 的挑战应答 | 无法应答 → 直接踢下线 |
| 断线重连的语义（同一设备恢复） | 重新登录 → 触发异地/多端校验 |

换句话说，QQ 判断「这是不是真人真设备」的依据，大半由**客户端进程**提供。
把客户端拿掉只留协议，等于把证据链抽走了。

### 4.2 三条存活路线

| 路线 | 做法 | 稳定性 | 主要风险 | 本仓库 |
|------|------|--------|----------|--------|
| **影分身**（headless） | 自实现登录 + qsign，如 Lagrange | 中：容易被踢 | 协议漂移、ToS | `arklink/ntqq/native.py`（研究态） |
| **Hook 客户端** | 注入官方客户端，与其共享会话，如 NapCat / LLOneBot | 高：客户端在即在 | 客户端更新导致 hook 失效 | 由协议端实现，本仓库通过 Milky/OneBot 使用 |
| **外部操作客户端** | 不注入，用 Win32/UIA 模拟键鼠操作已登录的客户端 | 高：不碰客户端内部 | 只发不收、抢焦点、依赖界面 | `arklink/ntqq/host.py` |

第三条路的价值在于**它不跟风控对抗**：客户端是用户自己登录的，程序只是在旁边
「帮你打字」。所以它不会因为协议被修、hook 被封而失效——只要 QQ 还开着。

### 4.3 本仓库的实现：`ntqq-client` 通道

```toml
[[adapters]]
type = "ntqq-client"
dry_run = false          # 校准热键后再关（默认 true：只记录不敲键盘）
search_hotkey = "^f"     # 唤起搜索；不同版本可能是 "^+f"
paste_hotkey = "^v"
process_names = ["QQ.exe"]
```

能力边界（写在代码里，也写在这里）：

- **只发不收**：收消息继续用 Milky / OneBot / 官方 API。它是「通知腿」，不是完整 bot；
- **只发文本**：图片/文件直接返回 `1404`，框架自动换通道，不会静默丢消息；
- **会抢焦点**：`open_and_send()` 会 `SetForegroundWindow`，演示/录屏时别开；
- **默认 dry-run**：不校准就挂上去，不会往任何窗口里乱敲字。

### 4.4 校准清单

| 项 | 为什么 | 怎么确认 |
|----|--------|----------|
| 搜索热键 | QQ NT 多为 `Ctrl+F`，个别版本 `Ctrl+Shift+F` | 手动按一次，焦点是否进搜索框 |
| 搜索结果排序 | 第一个结果未必是要找的人/群 | 先私聊自己或文件传输助手试 |
| 输入法状态 | 中文输入法会把号码变成候选词 | 切英文，或发送前先粘贴到搜索框确认 |
| 窗口恢复 | 最小化时 `SetForegroundWindow` 可能失败 | 代码里先 `ShowWindow(SW_RESTORE)` |
| 多开 | 多个 QQ.exe，需按 pid 选窗口 | `detect()` 返回 pid/hwnd，可指定 |

### 4.5 什么时候该用它

- 所有协议端同时失效，但用户的 QQ 还挂着 → 至少能把告警/通知发出去；
- 只读场景的反向验证：手动操作一遍，确认「消息确实到了」；
- **不要**用它做高频群发：界面操作慢、易错、且明显违反平台规则。

## 5. 逆向路线：QQ NT 原生协议

目标不是「再写一个 OneBot」，而是**把中间层也变成自己的**：
不依赖 NapCat/Lagrange，直接说 SSO。理论上这是抗封最强的一层，工程上也最难。

### 5.1 封包结构

```
offset  size  field
0       1     magic     0x02
1       4     length    从 seq 起算，到包尾 0x03 为止（不含 magic 与自身）
5       4     seq       自增序号，响应回填同值
9       4     cmd       指令号（登录/心跳/发消息各一条）
13      2     version   0x0001
15      4     uin       登录后为自己 QQ 号，登录前 0
19      N     body      TEA 加密的 protobuf
19+N    1     tail      0x03
```

NT 另有带 `uid` 字符串的变体（登录后使用）：body 前多一个「1 字节长度 + uid」段。
`arklink/ntqq/sso.py` 两种都能编解码，并且能处理 TCP 粘包。

### 5.2 TEA 加解密

QQ 用的是教科书 TEA 的**16 轮**变体（delta `0x9E3779B9`），分组之间做链接。
`arklink/ntqq/tea.py` 提供：

- `encrypt_block / decrypt_block`：单分组，可用公开测试向量验证
  （32 轮全零 → `41ea3a0a 94baa940`，单测里有）；
- `qq_tea_encrypt / qq_tea_decrypt`：填充 + `cbc` / `pcbc` 两种链接模式，
  填充支持 `qq`（末字节记长度）/ `pkcs7` / `zero`。

⚠️ **链接模式与填充必须与目标客户端对拍**。不同分支的实现细节有差异
（是异或上一块密文还是明文），选错了表现是「包头正常、body 全是乱码」。

### 5.3 签名（qsign）

登录与部分关键指令需要**设备指纹 + 包体**算出的签名，社区做法是外包给本地
qsign 服务：

```
GET /sign?uin=10001&qua=<设备qua>&cmd=wtlogin.login&seq=1&buffer=<hex>
→   {"code": 0, "value": {"sign": "<hex>", "token": "<hex>", "extra": "<hex>"}}
```

`arklink/ntqq/qsign.py` 实现了客户端（GET 失败自动退回 POST，三个字段都解码成
bytes）。**签名算法本身不在本仓库**，也不内置任何可用服务地址。

### 5.4 还差什么（`native.py` 为什么不能登录）

| 缺口 | 说明 | 难度 |
|------|------|------|
| 登录握手 | `wtlogin.trans_emp` 取二维码 → 轮询 → `wtlogin.login` 换票据 | 高 |
| 设备指纹 | android_id / guid / qua / 机型 的生成规则，风控强相关 | 高 |
| 密钥协商 | ECDH（secp192k1）→ 会话密钥 → 何时开始加密 body | 中高 |
| 业务 schema | 发消息/取历史的 protobuf 字段表 | 中（纯体力） |
| 心跳保活 | 间隔、超时、被踢的判定 | 低 |

所以 `NativeQQAdapter` 的定位是**脚手架而不是半成品**：

- `build_packet()` / `parse()` 打通「拼包 → 加密 → 发 → 收 → 解密 → 解包」全链路
  （`selftest()` 有单测）；
- `probe(cmd, body)` 可以直接把抓到的字节喂进去看结构；
- 挂载后 `call_api` 一律返回 `1404`，框架自动降级到其他健康通道，**不会把业务打死**。

### 5.5 风险提示

- **风控**：新设备、异地、频繁重连都会触发验证码/冻结，真实账号得不偿失；
- **版本漂移**：客户端一升级，cmd 号与 schema 就可能变，维护成本是持续的；
- **合规**：模拟登录通常违反 QQ 用户协议。本仓库只做协议研究与自有账号实验，
  不提供任何绕过风控、批量登录、营销群发的能力。

## 6. 对拍清单（判断「真的通了」）

逆向最容易的错觉是「包发出去了 = 成功」。逐项对拍：

| 检查项 | 方法 | 失败现象 |
|--------|------|----------|
| TEA 密文一致 | 同一 key/plain 与抓包逐字节比 | body 乱码、服务端直接断连 |
| 包头 length | `python -m arklink decode --hex ...` 看字段 | 服务端等更多字节 / 直接 reset |
| cmd 号正确 | 抓包比对同一动作的 cmd | 无响应或返回 `-1` |
| 签名三个字段 | qsign 返回值分别塞进 sign/token/extra | 登录返回「环境异常」 |
| 链接模式 | cbc / pcbc 各试一次 | 只有第一块正确 |
| 心跳间隔 | 观察是否被服务端主动断 | 30s~60s 后掉线 |

现成命令：

```bash
python -m arklink selftest                        # 密码学/封包/管线自检
python -m arklink decode --hex 0200... --key 0123456789abcdef --pb
python -m arklink pb --hex 089601120361726b
```

## 7. 继续做的优先级

1. **qr 登录（只读）**：先打通 `trans_emp` 二维码 + 轮询，拿到票据即可读群列表/好友列表。
   这是性价比最高的一步，也是验证签名/加密是否正确的最短路径；
2. **收消息**：订阅推送 cmd，把 `parse()` 的 protobuf 映射到 OneBot 事件；
3. **发消息**：字段最少、最容易对拍；
4. **设备指纹**：等前三步稳定后再碰，它决定「能不能长期活着」；
5. **多账号/多设备**：不建议。风险与收益完全不匹配。

---

## 8. 一句话选型建议

- 要**体验**：Milky（或 OneBot）——能力全，代价是随时可能失效；
- 要**不死**：官方 Bot API——能力受限，但不会因为逆向被修而消失；
- 要**研究**：NTQQ 原生——把它当成长期实验，不要当生产依赖；
- 要**「至少还能发出去」**：让官方客户端一直挂着，用 `ntqq-client` 当通知腿。

ArkBot 把三者放在同一个 `[[adapters]]` 数组里并行跑，谁健康用谁，
这就是这套框架对「协议会变」这件事的全部回答。
