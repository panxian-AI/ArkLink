# 两个仓库的关系

一句话：**ArkBot 是业务框架，ArkLink 是协议外挂层。** 一个管「机器人做什么」，
一个管「怎么连上 QQ」。它们可以一起用，也可以各自单独用。

## 1. 依赖方向

```
        你的插件（关键词回复 / AI 聊天 / 群管理 / 定时推送）
                            │
                    ┌───────▼────────┐
                    │     ArkBot     │  框架内核：事件、规则、消息链、调度、发件箱
                    │  （业务框架）   │  对外还能扮演 OneBot 11 服务端
                    └───────┬────────┘
                            │  适配器契约（鸭子类型，不 import 具体实现）
                    ┌───────▼────────┐
                    │    ArkLink     │  协议外挂层：milky / satori / ntqq-*
                    └───────┬────────┘
                            │
                  NapCat / Koishi / 官方 QQ 客户端 / 腾讯服务器
```

依赖是**单向**的，而且是**运行时**的：

- ArkBot 里**没有一行 import arklink**。它通过 entry point `arkbot.adapters`
  发现外部适配器，或者用点分路径 `"arklink.ntqq.hook:HookQQAdapter"` 加载；
- ArkLink 里**没有硬依赖 ArkBot**。只有真正要把事件交给框架时，才
  `from arkbot.event import Event`（`arklink/base.py` 里刻意写成运行时导入）。

结果是：**两个仓库都能单独安装、单独测试、单独发版。** 这是刻意的，不是巧合。

## 2. 三种组合方式

| 你的情况 | 装什么 | 代码里怎么写 |
|---------|--------|-------------|
| 上层是 NoneBot2 / Koishi，只想要一个 NapCat 替代品 | 只装 ArkLink | `arklink serve onebot`，上层改地址 |
| 想自己写业务插件 | ArkBot + 官方 Bot 通道 | 只装 ArkBot，用官方 API（合规但功能受限） |
| 想自己写业务插件 + 挂自己的号 | ArkBot + ArkLink | `bot.toml` 里加 `[[adapters]] type = "ntqq-hook"` |

第三种是完整形态：插件写在 ArkBot，通道由 ArkLink 提供，
通道换一个（milky → hook → native）插件不用改。

## 3. 职责边界（代码该放哪）

| 该做的事 | 放哪 | 原因 |
|---------|------|------|
| 触发规则、消息链、限流、定时、发件箱补发 | ArkBot | 与平台无关，业务方天天改 |
| 把一种协议翻译成统一事件 | ArkLink | 协议易变，需要快速跟进 |
| 进程注入、封包、加密、二维码登录 | ArkLink | 逆向/系统层，和业务无关 |
| OneBot 11 兼容层（对上层扮演协议端） | ArkBot | 它是「对外承诺」的一部分，要跟着框架稳定 |
| 独立 OneBot 11 服务端（不需要框架时） | ArkLink | 只装 ArkLink 的场景要有出口 |

一个判断标准：**「换一个 QQ 实现，这段代码要不要改？」**
要改 → 属于 ArkLink；不改 → 属于 ArkBot。

## 4. 版本是独立的

| | ArkBot | ArkLink |
|---|---|---|
| 当前版本 | 0.4.0 | 0.6.0 |
| 变化频率 | 低（业务 API 要稳） | 高（协议、注入、平台适配） |
| 升级动力 | 新插件能力 / 兼容层改进 | 新通道、反封、Linux 支持 |

所以升级/回退要**分开操作**：

```bash
python -m arklink update --to 0.5.0                      # 动 ArkLink
python -m arklink update --project arkbot --to 0.4.0     # 动 ArkBot
```

兼容性：ArkBot 0.4.0 起支持通过 entry point 发现 ArkLink，两者组合没有额外版本约束；
ArkLink 新增通道时不会要求 ArkBot 跟着升级（适配器契约保持鸭子类型）。
唯一要小心的是**回退 ArkBot 到 0.4.0 之前**：那时的适配器加载器还不存在，
`type = "ntqq-hook"` 会认不出来（回退检查会提示这一点）。

## 5. 出问题先看是谁

| 现象 | 大概率在 | 怎么确认 |
|------|---------|---------|
| 上层收不到事件、鉴权失败、WS 连不上 | ArkLink | 直接 `curl` / `ws` 打 OneBot 服务端，看日志 |
| 事件收到了但插件没反应、规则不匹配 | ArkBot | 看框架日志里的规则命中 |
| 通道连不上 QQ（进程/管道/注入） | ArkLink | `arklink hook --list` |
| 消息发不出去但通道是通的 | 两边都可能 | 先看返回值：`1404` = 通道不支持；其它 = 框架侧 |

## 6. 为什么拆成两个仓库

- **发版节奏不同**：协议层可能一周改三次，框架三个月才动一次。放一起会逼用户
  为了一个新通道升级整个框架，风险不对等；
- **安装体积与依赖不同**：只想当 NapCat 替代品的人不该被迫装整个框架；
- **可替换性**：ArkLink 除了 ArkBot，还能被别的框架当库用（`LinkAdapter` 契约
  不依赖任何框架）；ArkBot 也能不带 ArkLink，只用官方 Bot 通道跑。
