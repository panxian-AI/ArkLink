# 迁移验收清单（用户操作层面）

迁移完不能只看「服务起来了」。这份清单按**你会实际做的操作**逐项验证，
每项都写了「怎么做 / 应该看到什么 / 不对时查哪里」。

两类检查配合用：

```bash
python -m arklink doctor        # 自动：环境、模块、进程、管道、服务端、配置（10 项）
```

自动检查通过只代表「管道通了」，**收消息、发消息、异常场景必须手动过一遍**。
下面标 🤖 的是 doctor 已覆盖的，其余需要手动。

---

## A. 基础设施（5 分钟）

| # | 操作 | 预期 | 不对时查 |
|---|------|------|---------|
| A1 🤖 | `python -m arklink doctor` | 除「QQ 进程/管道」可能 SKIP 外全 OK | 按输出里的 → 建议逐条处理 |
| A2 | 打开官方 QQ 并登录 | 手机端能看到「电脑已登录」 | 登录态由客户端维持，ArkLink 不碰密码 |
| A3 🤖 | `python -m arklink hook --list` | 列出多个 `QQ.exe`，只有一个「主」 | 全部显示非主：命令行里都有 `--type=`，说明找错了进程 |
| A4 🤖 | `python -m arklink hook --install` | 打印「管道已连通 uin=…」 | `busy` = SnowLuma 还连着，先退掉；`missing` = 注入失败，看 DLL 是否被拦 |
| A5 | `python -m arklink serve onebot --port 6700 --token t` | 打印「OneBot 11 已就绪」 | 端口占用换 6701 |
| A6 🤖 | `curl -H "Authorization: Bearer t" http://127.0.0.1:6700/` | `{"status":"ok",...}` | 401 = token 不一致；连接拒绝 = 没起服务 |

## B. 收消息（核心，必须全过）

用另一个号（或手机）给你的 bot 号发消息，逐项确认上层框架能看到事件。

| # | 操作 | 预期（上层收到的事件） | 不对时查 |
|---|------|----------------------|---------|
| B1 | 私聊发「1」 | `message_type=private`，`message` 有 text 段 | 完全没有事件 → 通道没送包（hook 收包未接） |
| B2 | 群里发「2」 | `message_type=group`，`group_id` 正确 | group_id 是 0 → 群路由字段解析错 |
| B3 | 群里 @bot 发「3」 | 有 `at` 段且 `qq` 是 bot 号 | at 段变成 text → commonelem 分支没命中 |
| B4 | 发一张图片 | `image` 段（`file`/`url` 至少一个非空） | 空段 → offpic/customface 未映射 |
| B5 | 发一个表情/小表情 | `face` 段有 `id` | 变成文本 `[表情]` 也算可接受 |
| B6 | 引用 B2 的消息回复 | `reply` 段，`id` 指向被引用消息 | 没有 reply 段 → source elem 未解析 |
| B7 | 发完 2 分钟内撤回一条 | `notice/group_recall`（或 message 的 recall） | 没有 → ContentHead.Type==2 分支未触发 |
| B8 | 发文件 / 语音 / 视频 | 对应 `file`/`record`/`video` 段；不支持时至少保留事件不丢 | 整条事件消失 → 「未知段丢弃整条」的 bug |
| B9 | 发链接卡片 / 小程序 | `json` 或 `xml` 段（或至少纯文本兜底） | 无 → lightapp/richmsg 未处理 |
| B10 | 拉一个人进群 / 退群 | `notice/group_increase` / `group_decrease` | 无 → 群通知未订阅（当前可能未接） |
| B11 | 连续发 10 条 | 10 条事件，顺序一致，无丢失 | 丢包 → 看 `dropped` 计数与队列是否满 |
| B12 | 发一条 4000 字长文 | 事件完整（不截断）或明确分段 | 截断 → 帧长度上限 |

## C. 发消息（能力边界要清楚）

| # | 操作 | 预期 | 说明 |
|---|------|------|------|
| C1 | `POST /send_group_msg`（文本） | `retcode=0` + `message_id` | 当前 hook 只读会返回 `1404`，属预期 |
| C2 | 发送带 `at` 段 | 被 @ 的人收到提醒 | 同上 |
| C3 | 发送图片（本地路径 / URL） | 图片出现在群里 | 同上 |
| C4 | 引用一条消息发送 | 显示为引用 | 同上 |
| C5 | 连发 20 条 | 不被风控、不被吞 | 看是否触发频率限制；节律策略见 `docs/协议级封禁.md` |
| C6 | 未实现接口（如 `set_group_ban`） | `retcode=1404` | 上层据此降级，不能是 500 |

> 现在 `ntqq-hook` 是只读通道，C 组会整组返回 1404。**这是已知边界**，
> 不是配置错误。要验证「发送链路本身」，用 `milky` / `satori` 通道对照。

## D. 会话与异常（最容易漏）

| # | 操作 | 预期 | 不对时查 |
|---|------|------|---------|
| D1 | 关掉 QQ 再打开并登录 | 自动重新注入/重连，事件恢复 | 需要重启服务 → `poll_interval` 没生效 |
| D2 | 重启 `serve onebot`（QQ 不动） | 上层重连后事件恢复 | 上层不重连 → 心跳/关闭帧没发 |
| D3 | 拔网线 30 秒再插回 | 连接自愈，不产生重复事件 | 重复事件 → 断线重放逻辑 |
| D4 | 切换登录另一个 QQ 号 | `self_id` 变化，事件不串号 | 串号 → `self_id` 缓存没刷新 |
| D5 | 挂着不动 2 小时 | 心跳正常，内存不增长 | 内存涨 → 看事件队列/连接是否泄漏 |
| D6 | 上层用错 token 连接 | 被拒绝（1008 / 401），有日志 | 能连上 → 鉴权没生效 |
| D7 | 同时开两个上层客户端 | 两边都收到事件（广播） | 只有一边 → 客户端集合管理问题 |

## E. 上层框架专项

| # | 框架 | 操作 | 预期 |
|---|------|------|------|
| E1 | NoneBot2（正向 WS） | 配 `ws://127.0.0.1:6700/onebot/v11/ws` | 启动日志显示已连接，`nonebot run` 能响应命令 |
| E2 | NoneBot2（反向 WS） | 让 ArkLink 连 NoneBot 的 `/onebot/v11/ws` | 同上（当前版本只做正向，反向待办） |
| E3 | Koishi | OneBot 适配器填同一地址 | `koishi` 控制台显示 bot 在线 |
| E4 | AstrBot | 同上 | 平台状态「已连接」 |
| E5 | 自研脚本 | `POST /send_group_msg` + `GET /get_status` | 返回 OneBot 形状 |
| E6 | HTTP 上报模式 | `--report http://your/endpoint` | 每条事件都被 POST 一次 |

## 什么时候算「迁移完成」

- A、B、D 三组全过 → 收消息可用，可以并行跑（旧协议端先别删）；
- C 组全过 → 可以真正替换掉旧协议端；
- E 组全过 → 上层框架确认无感。

现在的状态：**A、B 大部分可过，C 整组返回 1404**（只读通道），
所以结论是「可以接进来验证，还不能替换生产」。进度见
[协议级封禁.md](协议级封禁.md)。
